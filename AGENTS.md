# Память проекта

Согласованный с пользователем план находится в [docs/project-plan.md](docs/project-plan.md).
Перед работой прочитайте его: там зафиксированы стек, архитектура, ограничения,
девять этапов и критерии их завершения.

## Сообщения коммитов и релизы

- Все новые коммиты, в том числе созданные агентом, оформляйте по
  [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):
  `type(scope): description`. Scope необязателен, например `feat: add application scaffold`,
  `fix(backend): handle shutdown errors`, `docs: describe local setup`.
- `feat` — новая возможность, `fix` — исправление ошибки. Для остальных изменений
  используйте `docs`, `chore`, `ci`, `build`, `test`, `refactor`, `perf`, `style`
  или `revert` по смыслу. В проекте type пишется строчными буквами.
- Несовместимые изменения обозначайте `!` перед двоеточием или футером
  `BREAKING CHANGE: описание`; явно объясняйте изменение и необходимую миграцию.
  Body и футеры отделяйте пустой строкой. Не помечайте обычный рефакторинг как `feat`.
- Заголовки PR также должны соответствовать этому формату. При squash merge
  используйте заголовок PR как заголовок итогового коммита; проверяйте также body.
  Не переписывайте исходную историю Хекслета ради соответствия формату.
- Перед коммитом проверяйте его сообщение через `make commitlint` (stdin),
  историю после принятия соглашения — через `make commits-check`.
  Подготовка инструментов: `make tooling-build tooling-install`.
- Версию приложения задаёт `version.txt`. Общий `CHANGELOG.md` и release-PR
  поддерживает отдельный workflow release-please. Не изменяйте версии вручную
  для обычных задач и не сливайте release-PR без запроса пользователя.
  Подробности и правила SemVer: [docs/releases.md](docs/releases.md).

## Работа по этапам

- Когда пользователь просит выполнить этап N, выполняйте этот этап с учётом уже
  завершённых этапов. Не переходите автоматически к следующему этапу.
- Перед изменениями проверяйте состояние репозитория и фактическое выполнение
  зависимостей этапа. Не считайте статус в плане заменой проверки.
- После работы обновляйте статус и журнал соответствующего этапа в плане:
  изменения, выполненные проверки, их результат и оставшиеся действия.
- Отмечайте этап завершённым только после выполнения его критериев. Если нужна
  внешняя авторизация, настройка GitHub или перезапуск MCP-клиента, явно запишите
  непроверенную часть; не выдавайте конфигурацию за работающую интеграцию.
- Сохраняйте важные решения в плане, чтобы следующая сессия могла продолжить
  работу без истории переписки. Не сохраняйте секреты, токены и локальные
  абсолютные пути в документации или конфигурации репозитория.

## Согласованные ограничения

- На данном этапе нужен только технический каркас, без бизнес-логики календаря,
  бронирования, пользователей, авторизации, базы данных и фиктивных сущностей.
- Frontend и backend размещаются в отдельных каталогах.
- Инструменты разработки, зависимости, линтеры, тесты и сборка запускаются в
  Docker-окружении. Не устанавливайте библиотеки проекта глобально на хосте.
- Backend использует слои api, usecase, services, repo и domain; правила
  зависимостей приведены в плане.
- Не изменяйте и не удаляйте `.github/workflows/hexlet-check.yml` и не
  переименовывайте репозиторий: это требования существующего проекта Хекслета.
- Пока пользователь просит только планирование или сохранение плана, не
  приступайте к реализации. Создание этого файла и плана не означает, что
  какой-либо из девяти этапов уже выполнен.
