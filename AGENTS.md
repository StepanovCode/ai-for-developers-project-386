# Правила работы над Meetly

Meetly — сервис записи на звонки. Frontend: React, TypeScript, Vite, shadcn/ui;
backend: Go, Gin и PostgreSQL. Контракт API описан в TypeSpec.

## Перед изменениями

- Проверьте ветку, `git status` и фактический код; сохраняйте изменения пользователя.
- Выполняйте запрошенную задачу или этап, учитывая уже реализованные возможности.
  При запросе только планирования ограничьтесь планом.
- Изучите затронутые модули и их тесты. Важные решения и результаты проверок
  фиксируйте в описании PR; явно указывайте непроверенные части и внешние действия.
- При работе с предметной областью используйте термины из [GLOSSARY.md](GLOSSARY.md)
  в коде, тестах, интерфейсе и документации.

## Issue tracker: GitHub

- Трекер — [GitHub Issues](https://github.com/StepanovCode/ai-for-developers-project-386/issues).
  Спецификации и решения публикуйте в Issues; локальный черновик не заменяет публикацию.
- Перед продолжением [карты решений](https://github.com/StepanovCode/ai-for-developers-project-386/issues/3)
  прочитайте её Destination и Notes; подробности вопросов загружайте по необходимости.
- Карта имеет метку `wayfinder:map`, вопросы — native sub-issues с метками
  `wayfinder:grilling`, `wayfinder:research`, `wayfinder:prototype` или `wayfinder:task`.
  Создавайте нужные метки и вопросы до связей; блокировки задавайте native dependencies
  (`blocked by`, в UI: Relationships → Mark as blocked by).
- Frontier: открытые sub-issues без открытых блокировок и assignee, в порядке карты.
  Claim: перед работой назначьте вопрос ведущему разработчику.
- Resolve: опубликуйте ответ комментарием, закройте вопрос и добавьте в
  Decisions so far карты строку с сутью и ссылкой на ответ. Детали храните в вопросе;
  карта служит индексом. В тексте для человека ссылайтесь на вопросы по названию.
- HITL-вопросы обсуждайте с пользователем; спецификацию считайте утверждённой
  только после явного ответа о конкретной опубликованной версии.
- Проверяйте актуальный доступ: используйте авторизованный GitHub API, connector
  или `gh`; при отсутствии операции — авторизованный браузер с той же моделью связей.
- Исследовательские отчёты публикуйте в ветке `research/<name>`; в ответе вопроса
  давайте ссылку на файл в конкретном коммите. Проверка документации и успешный
  запуск инструментов в проекте — отдельные результаты.

## Чистая архитектура

- Frontend и backend остаются в отдельных каталогах. Frontend обращается
  к относительному `/api` через generated SDK; доступ к PostgreSQL — только в `repo`.
- `domain` содержит типы и чистые бизнес-правила, без зависимостей от HTTP,
  БД и других внутренних слоёв.
- `api` отвечает за Gin, маршруты, HTTP DTO, валидацию формата и статусы;
  бизнес-сценарии вызывает через `usecase`. Технический health остаётся в `api`.
- `usecase` координирует сценарии; `services` содержит самостоятельные
  повторно используемые операции. Оба работают с `domain` и небольшими
  интерфейсами, объявленными рядом с потребителем; конкретный `repo` не импортируют.
- `repo` реализует эти интерфейсы и скрывает SQL/pgx; не вызывает прикладные слои.
  `services` не зависит от `usecase`; внутренние слои не зависят от `api`.
- `cmd/api` явно собирает зависимости через конструкторы и управляет сервером;
  `config` читает технические настройки без зависимостей от других внутренних слоёв.
- Внутрь передавайте `context.Context` и доменные типы; Gin, HTTP DTO
  и типы хранения оставляйте в соответствующих адаптерах.
- Допустимы вызовы `api → usecase → services → repo` и `usecase → repo`
  через интерфейсы. Направление вызовов не определяет направление импортов.

## KISS и поддерживаемый код

- Выбирайте простое решение текущей задачи с ясными именами и явными зависимостями.
  Добавляйте абстракцию, слой или зависимость только для конкретной потребности.
- Сервис должен иметь собственную ответственность; избегайте обёрток,
  которые лишь перенаправляют вызов, и фиктивных сущностей для заполнения слоёв.
- Держите бизнес-правило в одном месте. Разделяйте расчёты и побочные эффекты;
  передавайте часы и внешние зависимости явно, когда от них зависит поведение.
- Обрабатывайте ошибки явно: клиент получает безопасный ответ,
  технические подробности остаются в логах. Ошибка БД не заменяется успехом в памяти.
- Изменяйте `api/main.tsp`, затем выполняйте `make generate`; generated-файлы
  сохраняйте вместе с контрактом, без ручного редактирования. Детали — в `api/README.md`.
- Миграции добавляйте новыми последовательными файлами;
  уже применённый SQL сохраняйте неизменным.

## Тестирование и проверка

- Для изменения поведения добавляйте тест наблюдаемого результата;
  исправление ошибки сопровождайте регрессионным тестом, воспроизводящим её.
- Frontend проверяйте Vitest и React Testing Library через действия пользователя,
  доступные роли и видимый результат; backend — `testing` и `httptest`.
- Покрывайте правила, границы, ошибки и важные переходы состояния.
  Тестируйте публичное поведение, а не приватную реализацию или порядок вызовов.
- Время задавайте явно. Интеграционные тесты выполняйте только на отдельной
  `postgres-test/booking_test` с настоящими миграциями; рабочую БД не очищайте
  и тестовыми данными не наполняйте. Ограничения и конкуренцию проверяйте в PostgreSQL.
- Все зависимости, генераторы, линтеры, тесты и сборки запускайте в Docker через Make.
  Проектные библиотеки и инструменты на хост не устанавливайте.
- Для кода запускайте `make frontend-check` или `make backend-check` по области
  изменений; для обеих частей — `make check`, для хранения — `make database-test`.
  Изменения интерфейса дополнительно проверяйте в браузере: мобильная ширина,
  клавиатура, прямые ссылки и перезагрузка. Для текстовых правок достаточно проверки diff.
- Перед завершением выполните `git diff --check`; сообщайте команды и фактические
  результаты. Конфигурация без успешного запуска не подтверждает интеграцию.

## Git и релизы

- Коммиты и заголовки PR: Conventional Commits `type(scope): description`,
  type строчными буквами. При squash используйте корректный заголовок PR.
  Несовместимость обозначайте `!` или `BREAKING CHANGE:` с описанием миграции.
- Перед коммитом проверяйте сообщение через `make commitlint` (stdin);
  подготовка: `make tooling-build tooling-install`. Историю Хекслета не переписывайте.
- Версия — `version.txt`; версии, общий `CHANGELOG.md` и release-PR обновляет
  release-please. Обычные задачи не меняют версии вручную;
  release-PR сливайте только по запросу пользователя.
- Сохраняйте `.github/workflows/hexlet-check.yml` и имя репозитория неизменными.
  Секреты и локальные абсолютные пути в Git не сохраняйте;
  `.codex/` и `.superpowers/` остаются локальными и исключены из отслеживания.
