# План создания каркаса приложения

Дата фиксации: 2026-09-25.

## Цель и границы

Создать современный технический каркас frontend/backend-приложения, который
воспроизводимо запускается, собирается, тестируется и проверяется линтерами,
публикуется в GitHub и получает release-PR через release-please.

Бизнес-логику не реализуем. В рамках плана нет календаря, бронирований,
пользователей, авторизации, базы данных, миграций и интеграций предметной области.
Разрешён минимальный технический код: стартовая страница, health endpoint,
конфигурация, запуск сервера и дымовые тесты.

Пользователь будет запускать этапы в отдельных сессиях. Выполнять только
запрошенный этап; после него сохранять результат здесь. Этот документ — память
проекта, а не свидетельство выполнения ещё не запущенных работ.

## Согласованные решения

### Окружение и стек

- Монорепозиторий с отдельными `frontend/` и `backend/`.
- Изоляция через Docker Compose. Python venv для Node.js и Go не используется.
- На хосте необходим Docker с Compose; проектные Node.js, Go, зависимости и
  инструменты запускаются в контейнерах.
- Исходники доступны контейнерам через bind mounts; `node_modules`, кеши npm,
  Go-модулей и Go-сборки хранятся в volumes проекта.
- Версии инструментов закрепляются при реализации после проверки совместимости.
- Frontend: Vite, React, TypeScript, npm, Tailwind CSS и shadcn/ui.
- Backend: Go, Gin, стандартный HTTP-сервер с таймаутами и graceful shutdown.
- Frontend-тесты: Vitest и React Testing Library; backend: testing и httptest.
- Качество: ESLint, TypeScript typecheck, Prettier, golangci-lint и форматирование Go.
- MCP: официальный shadcn MCP и официальный GitHub MCP Server с toolset `actions`.
- Релизы: одна версия приложения, общий changelog, release-please со стратегией
  `simple`, `version.txt` и manifest-конфигурацией.

### Архитектура backend

Предпочтение пользователя: `api -> usecase -> services -> repo`; прямой вызов
репозитория из `usecase` также допустим. Название Go-пакета — `usecase`, без
подчёркивания. Структура:

```text
backend/
  cmd/api/main.go
  internal/
    api/
      handlers/
      middleware/
      router.go
    usecase/
    services/
    repo/
    domain/
    config/
  go.mod
  go.sum
```

Ответственность и ограничения:

- `api`: Gin, маршруты, HTTP DTO, проверка формата входных данных, ответы и
  преобразование ошибок в HTTP-статусы.
- `usecase`: сценарии приложения и координация сервисов/репозиториев.
- `services`: повторно используемые операции с самостоятельной ответственностью.
  Сервис не нужен, если он только перенаправляет вызов репозиторию.
- `repo`: конкретные реализации доступа к хранилищам.
- `domain`: независимые от HTTP и хранения сущности, типы и доменные правила.
- `config`: техническая конфигурация приложения.
- `cmd/api`: точка входа и явная сборка зависимостей через конструкторы.
- Направление вызовов не равно направлению импортов: `usecase` и `services`
  работают через небольшие интерфейсы, объявленные рядом с потребителем, и не
  импортируют конкретные реализации из `repo`.
- Реализации репозиториев удовлетворяют этим интерфейсам неявно, как принято в Go.
- `services` не зависят от `usecase`; `repo` не вызывает сценарии приложения.
- Gin и `gin.Context` остаются в `api`. Внутрь передаются `context.Context` и
  обычные типизированные данные, без HTTP- и ORM-зависимостей.
- Сервис, обращающийся к репозиторию, относится к прикладному слою. Чистые
  доменные правила размещаются в `domain`.
- В каркасе будущие бизнес-слои обозначаются документацией, без выдуманных
  интерфейсов и реализаций. Пустые каталоги Git не сохраняет: при необходимости
  использовать README с назначением слоя.
- `GET /api/health` — технический маршрут уровня `api`; искусственно проводить
  его через usecase/services/repo не требуется.

## Этап 1. Создать изолированное окружение Docker Compose

Работы:

- Проверить доступность Docker/Compose. При отсутствии записать требуемое
  действие по установке или запуску Docker, не заменять изоляцию глобальной
  установкой Node.js, Go или библиотек.
- Подготовить окружения Node.js и Go, Compose-конфигурацию, необходимые
  Dockerfile и `.dockerignore`.
- Настроить рабочие каталоги, mounts исходников, отдельные volumes зависимостей
  и кешей. Для команд установки выбирать контейнеры, не требующие существования
  ещё не созданного приложения.
- Предусмотреть порты frontend/backend, доступ браузера с хоста и работу Vite
  внутри контейнера. Dev-сервер приложения подключается на этапе 3.
- Описать команды входа в окружение, остановки и удаления ресурсов именно
  этого проекта. Не использовать глобальный Docker prune.
- Предусмотреть выполнение shadcn CLI/MCP в контейнере на этапе 7.

Критерии завершения:

- Compose-конфигурация валидна, Node.js/npm и Go запускаются в контейнерах.
- Контейнеры видят исходники и используют предусмотренные каталоги кешей.
- Для работы окружения не нужны глобально установленные зависимости проекта.
- Документированы запуск, остановка и явная очистка volumes проекта.
- Запуск самих приложений не является критерием этапа 1: их ещё нет.

Работы:

- Для squash merge зафиксировать использование корректного заголовка PR в
  итоговом сообщении коммита.
- Добавить отдельный `.github/workflows/ci.yml` на каждый `push` и
  `pull_request`, с независимыми заданиями frontend/backend.
- В CI выполнять воспроизводимую установку зависимостей, линтеры, проверку
  форматирования, typecheck frontend, тесты и сборку. Использовать согласованные
  контейнерные команды и версии инструментов.
- Опубликовать изменения в рабочей ветке GitHub, проверить реальные результаты
  Actions и при доступности MCP прочитать их через него.
- Сохранить `.github/workflows/hexlet-check.yml` без изменений.

Критерии завершения:

- Новый CI реально запускается на push и PR; все новые обязательные задания
  проходят. Ссылки на PR/запуски записаны в журнале.
- Conventional Commits проверяются автоматически, включая заголовок PR.
- Непроверенные настройки или отсутствие доступа к GitHub явно отмечены.

## Этап 9. Настроить release-please и проверить release-PR

Работы:

- Добавить отдельный `.github/workflows/release-please.yml` на push в `main`
  с официальным `googleapis/release-please-action`.
- Настроить manifest, стратегию `simple` для одной версии приложения, общий
  `CHANGELOG.md` и `version.txt`. Определить начальную версию и точку отсчёта
  так, чтобы первый релизообразующий коммит каркаса вошёл в обработку.
- Версия приложения определяется `version.txt`; если версия frontend package
  синхронизируется с ней, настроить согласованное обновление package.json и
  lockfile и проверить последующий `npm ci`.
- Проверить разрешения GitHub на создание release-PR и релизов.
- Для автоматического CI на release-PR использовать GitHub App token или
  подходящий PAT в GitHub Secrets: события от стандартного `GITHUB_TOKEN`
  обычно не запускают последующие workflow.
- Провести PR с каркасом через CI и merge в `main`. В истории должен быть
  реальный релизообразующий Conventional Commit, например
  `feat: initialize application scaffold`; одни `chore`/`ci` по умолчанию
  могут не создать release-PR.
- После merge проверить запуск release-please, появление release-PR,
  корректность версии/changelog и CI на этом PR.

Критерии завершения:

- Есть реально созданный release-PR в `main`, содержащий ожидаемое обновление
  версии и changelog; его CI успешно завершился.
- В журнале сохранены ссылки на исходный PR, workflow run и release-PR.
- Для завершения этого этапа не требуется автоматически сливать release-PR,
  публиковать пакеты или развёртывать приложение.
