# Структура и архитектурные границы

Монорепозиторий содержит независимые frontend и backend. Frontend реализован
как техническая стартовая страница; backend содержит HTTP-сервер и health endpoint.

```text
frontend/                 Vite + React + TypeScript (этап 3)
backend/
  cmd/api/                точка входа и сборка зависимостей (этап 4)
  internal/
    api/
      handlers/           HTTP-обработчики
      middleware/         HTTP middleware
    usecase/              сценарии приложения
    services/             повторно используемые прикладные операции
    repo/                 реализации доступа к хранилищам
    domain/               независимые доменные типы и правила
    config/               техническая конфигурация
docker/                   образы окружения разработки
docs/                     план, архитектура, инструкции
compose.yaml              общие контейнеры для разработки и будущего CI
Makefile                  интерфейс к контейнерным командам
```

`frontend/package.json` и `package-lock.json` созданы на этапе 3;
`backend/go.mod`, `go.sum`, `cmd/api/main.go` и
`internal/api/router.go` созданы на этапе 4.
README сохраняют пустые слои в Git и объясняют их назначение.

## Frontend

Frontend отвечает за отображение и взаимодействие с HTTP API. Он не импортирует
код backend. На этапе 3 добавлены Tailwind CSS, shadcn/ui, alias `@/` и
минимальная техническая страница. Структуру компонентов определяем по мере
появления реального кода, без фиктивных страниц и сущностей.

Браузер обращается к относительному `/api`; Vite проксирует запросы к
`http://backend:8080` в сети Compose. Proxy настроен на этапе 3, а сквозная
проверка выполнена на этапе 4: `/api/health` возвращает HTTP 200 и JSON.

## Backend

Направление вызовов: `api -> usecase -> services -> repo`. Вызов
`usecase -> repo` также допустим. Направление импортов отличается от вызовов:
прикладные слои зависят от интерфейсов рядом с потребителем, а не от конкретного
пакета `repo`. Реализации удовлетворяют интерфейсам неявно.

| Слой | Ответственность и допустимые зависимости |
|---|---|
| `cmd/api` | Конфигурация, сборка конкретных зависимостей через конструкторы, запуск и остановка сервера. Может связывать все слои. |
| `api` | Gin, маршруты, HTTP DTO, проверка формата ввода, HTTP-статусы. Вызывает `usecase`; не обращается напрямую к хранилищу. |
| `usecase` | Координация сценариев; использует `services`, `domain` и собственные интерфейсы доступа к данным. Не импортирует конкретный `repo` или API. |
| `services` | Самостоятельные повторно используемые операции; `domain` и собственные интерфейсы доступа к данным. Не импортирует `usecase`, `repo` или API. |
| `repo` | Конкретный доступ к хранилищам, может использовать `domain`. Не импортирует и не вызывает прикладные слои и API. |
| `domain` | Независимые типы и правила, без зависимостей от остальных слоёв, HTTP и хранения. |
| `config` | Технические настройки, без зависимостей от остальных внутренних пакетов; читаются в точке входа. |

Gin и `gin.Context` остаются в `api`; внутрь передаются `context.Context` и
обычные типизированные данные. HTTP DTO и ORM-типы не переходят в прикладные
и доменные слои. Общие типы при необходимости размещаются в `domain`.

Сервис добавляется только при самостоятельной ответственности, а не ради
перенаправления вызова репозиторию. Сервис с доступом к репозиторию относится
к прикладному слою; чистые доменные правила — к `domain`.

`GET /api/health` — технический маршрут API. Для него не нужны usecase,
сервис, репозиторий и доменная сущность. В каркасе нет календаря, бронирований,
пользователей, авторизации, базы данных, миграций и фиктивных интерфейсов.

Источник согласованных решений и критериев: [план проекта](project-plan.md).
