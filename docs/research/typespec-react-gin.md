# TypeSpec → OpenAPI → React SDK и Go/Gin

Дата исследования: 2026-10-04.
Контекст: [Исследовать цепочку генерации TypeSpec для React и Go/Gin](https://github.com/StepanovCode/ai-for-developers-project-386/issues/10),
дочернее исследование [карты спецификации](https://github.com/StepanovCode/ai-for-developers-project-386/issues/3).

Это исследовательская рекомендация для обсуждения и будущей реализации.
Проверены официальные документы и исходники; инструменты не устанавливались,
генерация и тесты не запускались. Работоспособность связки в проекте пока
не подтверждена. Код, зависимости и конфигурация приложения не изменены.

## Рекомендация

Использовать TypeSpec как единственный редактируемый источник HTTP-контракта,
`@typespec/openapi3` для OpenAPI **3.0.0**, Hey API для SDK с функциями операций,
`oapi-codegen` для Go DTO и Gin-адаптера, `gin-middleware` для проверки входящих
запросов по той же сгенерированной схеме. Это вывод исследования, а не уже
утверждённое продуктовое решение.

Выбор Hey API позволяет буквально выполнить требование «SDK генерируется»:
генерируются функции запросов, а не только декларации типов.
Плагин SDK использует `operationId` для структуры и имён операций и поддерживает
генерацию вызовов валидаторов; проверка в runtime включается отдельно.
[Документация SDK](https://heyapi.dev/docs/openapi/typescript/plugins/sdk).

На стороне Go предлагаются флаги `models`, `gin-server`, `strict-server`,
`embedded-spec`. Они создают DTO, интерфейсы и регистрацию маршрутов,
типизированные объекты запросов/ответов и встроенную спецификацию.
Реализацию сценариев пишет разработчик в отдельных файлах. `strict-server`
нужно включать вместе с конкретным сервером; он **не заменяет проверку входящих
запросов по схеме**. Для Gin предусмотрен отдельный middleware.
[oapi-codegen](https://github.com/oapi-codegen/oapi-codegen),
[схема конфигурации](https://github.com/oapi-codegen/oapi-codegen/blob/main/configuration-schema.json).

Проверка запросов здесь получается из спецификации через middleware и embedded
schema, а не как отдельная сгенерированная функция для каждого поля. Это надо
явно отразить в критерии реализации требования о серверных артефактах.

## Диалекты и версии

| Участок | Установлено по официальным источникам | Следствие для проекта |
|---|---|---|
| TypeSpec emitter | Опция `openapi-versions`; документированный default — `3.0.0`, доступны также `3.1.0` и `3.2.0` | Явно закрепить `3.0.0`, выходной путь и формат YAML в конфигурации |
| oapi-codegen | Релиз `v2.8.0` добавляет первоначальную поддержку OpenAPI 3.1; требует Go 1.25 и runtime не ниже 1.6.0 | Утверждение «oapi-codegen поддерживает только 3.0» устарело; для этой задачи возможности 3.1 пока не нужны |
| Hey API | Требует Node.js 22+, рекомендует точное закрепление версии; пакет находится в initial development | Node.js проекта 24.21.0 удовлетворяет опубликованному минимуму, но установка ещё не проверена |
| Текущее приложение | В `backend/go.mod` указаны Go 1.27.1 и Gin 1.12.0; frontend использует React 19, TypeScript 6 | Минимум Go удовлетворён; совместимость всей выбранной матрицы надо проверить запуском |

Источники: [опции emitter](https://typespec.io/docs/emitters/openapi3/reference/emitter/),
[релиз oapi-codegen v2.8.0](https://github.com/oapi-codegen/oapi-codegen/releases/tag/v2.8.0),
[Hey API installation и versioning](https://heyapi.dev/docs/openapi/typescript/get-started),
[версии проекта](../toolchain.md).

OpenAPI 3.0.0 рекомендуется как достаточный общий знаменатель для простых
JSON-моделей этого приложения, а не из-за запрета 3.1. При выборе 3.1 нужно
отдельно доказать совместимость генератора, runtime и версии `kin-openapi`,
которую использует middleware. Возможность прочитать документ ещё не доказывает
одинаковую проверку всех его конструкций. Ссылки на `main` показывают состояние
разработки; их нельзя использовать как закреплённую версию зависимости.

Точные npm-версии TypeSpec, его библиотек и Hey API, а также версии middleware
и runtime следует зафиксировать после минимальной проверки связки в Docker.
`v2.8.0` — проверенный по release notes кандидат для Go-генератора, а не
проверенная здесь установка. Плавающие `latest`, `^` и `~` не сохранять.

## Форматы и границы проверки

| Область | Предлагаемое правило контракта | Что проверить при реализации |
|---|---|---|
| Идентификаторы | Строковые непрозрачные значения; окончательный формат решает продуктовая спецификация | Не пропускать 64-битные числовые ID через JavaScript `number` |
| Длительность | Положительный `int32` в минутах, с согласованными минимумом и максимумом | Ноль, отрицательные, дробные и выходящие за пределы значения |
| Момент встречи | `utcDateTime` → строка `date-time`; в ответах договориться о нормализации в UTC | `Z`, смещение, некорректная дата, секунды/точность; не считать строку объектом JS `Date` |
| Календарный день | `plainDate` → строка `date` | День вычисляется в согласованном часовом поясе владельца, а не автоматически в UTC |
| Необязательные поля | Различать отсутствие свойства и явно допустимое `null` | `missing`, `null`, пустая строка и значение — отдельные случаи |
| JSON-модели | Простые именованные модели и enum; избегать сложных пересекающихся union без необходимости | Отсутствие `any`/потери ограничений, одинаковая сериализация TS и Go |
| Ошибки | Единая JSON-модель с устойчивым машинным кодом; HTTP-статусы перечислить для каждой операции | Ошибки middleware, binding и сценария должны иметь согласованный внешний вид |

TypeSpec документирует преобразование `plainDate`, `utcDateTime`, `int32`
и поддержку ограничений схемы; обе разновидности datetime с UTC/offset
становятся `format: date-time`. Следовательно, требование «только UTC» нельзя
выводить из одного этого формата. [Отображение типов TypeSpec в OpenAPI](https://typespec.io/docs/emitters/openapi3/openapi/).

В OpenAPI 3.0 разрешение `null` задаётся `nullable`, а обязательность свойства
— `required`; это разные измерения. [OpenAPI 3.0 Schema Object](https://spec.openapis.org/oas/v3.0.3.html#schema-object).
Для трёх состояний в Go существует `nullable.Nullable`, отличающий отсутствие,
`null` и значение. Не добавлять эту сложность, если у продукта нет такой
семантики. [oapi-codegen/nullable](https://github.com/oapi-codegen/nullable).

Для TS безопасный исходный договор — даты остаются строками на границе API.
Например, `openapi-typescript` по умолчанию генерирует `string` для `date-time`;
замена только декларации на `Date` не выполняет преобразования JSON.
[Node API и пример Date](https://openapi-ts.dev/node).
В Go генератор отображает `date-time` в `time.Time`; результат для принятого
контракта всё равно следует проверить. [Таблица type-mapping](https://github.com/oapi-codegen/oapi-codegen/blob/main/docs/configuration.md).

Middleware Gin вызывает `openapi3filter.ValidateRequest`; поддерживает
собственный `ErrorHandler`. По умолчанию ошибки возвращаются в его собственном
формате, поэтому адаптер общей модели ошибок остаётся рукописным кодом уровня
`api`. Источник также предупреждает о проверке Host при наличии `servers`:
схему и регистрацию маршрутов нужно проверить как напрямую, так и через
Vite proxy. Подавление предупреждения само по себе проверку Host не отключает.
[Исходник gin-middleware](https://raw.githubusercontent.com/oapi-codegen/gin-middleware/main/oapi_validate.go).

Схема может проверить типы, обязательность и статические ограничения. По выводу
исследования, правило «слот сейчас свободен», границы ближайших 14 дней,
существование типа события и атомарная защита от двух одновременных бронирований
должны оставаться в сценариях/домене и хранилище. Они зависят от времени и
состояния системы. Генерация не создаёт эту бизнес-логику.

Генерируемые HTTP DTO остаются внутри `api`; преобразование в доменные типы
происходит на этой границе. Не передавать Gin или генерируемые транспортные
объекты в `domain` и не строить доменные сущности как aliases DTO.
Это применение уже согласованных [архитектурных границ](../project-plan.md).

## Альтернатива для frontend

`openapi-typescript` генерирует TS-типы из OpenAPI 3.0/3.1 без runtime-кода.
`openapi-fetch` использует их для типизированных HTTP-вызовов вида
`client.GET(...)`, работает с React и возвращает `data`, `error`, `response`.
[Генератор типов](https://openapi-ts.dev/introduction),
[типизированный fetch](https://openapi-ts.dev/openapi-fetch/).

Это компактная альтернатива, если участники согласуют, что «SDK» означает
типизированный универсальный клиент со сгенерированными типами. Именованные
функции операций такой вариант сам не генерирует; рукописные обёртки добавят
поддерживаемый вручную слой. При буквальном требовании генерировать SDK
предпочтителен Hey API. Не подключать оба подхода одновременно.

## Предлагаемый воспроизводимый pipeline

Следующие имена и каталоги — предложение, пока не существующие команды.

1. Редактируемые исходники хранить в `api/`: TypeSpec, конфигурации emitter,
   SDK и Go-генератора. В конфигурациях явно указать стабильные пути вывода.
2. `make api-generate` последовательно запускает в Docker: установку закреплённых
   инструментов из lockfiles, TypeSpec compile, Hey API от полученного локального
   OpenAPI, oapi-codegen от того же файла, предусмотренное форматирование.
   Make должен сохранять эту последовательность и при `make -j`.
3. Предлагаемые результаты: `api/generated/openapi.yaml`,
   `frontend/src/api/generated/`, `backend/internal/api/generated/`.
   Рукописные адаптеры держать снаружи каталогов generated.
4. Исходники, конфигурации, lockfiles и generated-файлы сохранять в Git.
   Изменение контракта и его производных должно проверяться одним PR.
   Генерируемое руками не редактировать: исправлять источник или конфигурацию.
5. `make api-check` в CI повторяет генерацию в чистом временном каталоге и
   сравнивает весь набор файлов с сохранённым результатом. Проверять добавления,
   удаления и содержимое: одного `git diff` недостаточно для новых untracked
   файлов. Второй запуск должен дать тот же набор байтов.
6. Затем запускать TS typecheck/build и Go build/test. Генерация должна работать
   без запущенного API, БД, GitHub или размещённой в облаке спецификации.

Это проектное предложение, опирающееся на существующее требование запускать
инструменты через Docker. TypeSpec рекомендует сохранять lockfile и использовать
`npm ci` для контроля согласованности. [TypeSpec reproducibility](https://typespec.io/docs/handbook/reproducibility/).
Hey API допускает входную спецификацию из файла; облачный registry для этого
pipeline не требуется. [Настройка input](https://heyapi.dev/docs/openapi/typescript/configuration/input).

## Критерии будущей проверки

- Проверить минимальный контракт, включающий успешный JSON-ответ, ошибку,
  path/query/body, datetime, optional и nullable, до написания рабочих сценариев.
- Скомпилировать SDK и Gin strict-адаптер выбранными закреплёнными версиями.
  Через настоящий router и middleware проверить валидный запрос и отклонение
  неверного типа, отсутствующего обязательного поля, нарушенного диапазона,
  неверной даты и запрещённого `null`.
- Проверять тела и статусы ответов интеграционными тестами по контракту:
  строгий интерфейс не доказывает правильность всех значений ответа.
- Наличие каждой операции владельца и гостя связать с пользовательской историей
  и приёмочным сценарием после продуктовых решений карты.
- Отдельно проверить окно времени, соседние интервалы и гонку двух запросов:
  тест схемы не доказывает отсутствие двойного бронирования.
- Проверить pipeline с чистого checkout, повторную генерацию без изменений и
  обнаружение намеренно устаревшего/добавленного/удалённого артефакта в CI.

Исследование отвечает на вопрос о возможной технической цепочке. Оно не
утверждает модель данных, расписание, правила пересечения или итоговую
спецификацию приложения; эти решения остаются в соответствующих тикетах карты.
