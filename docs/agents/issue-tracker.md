# Issue tracker: GitHub

Трекер проекта — [GitHub Issues](https://github.com/StepanovCode/ai-for-developers-project-386/issues).
Выбор подтверждён пользователем 2026-10-04. Спецификации и решения публикуются
в Issues; локальные черновики не заменяют опубликованные вопросы.

Активная [карта решений: утверждённая спецификация приложения «На связи»](https://github.com/StepanovCode/ai-for-developers-project-386/issues/3).
Перед продолжением загрузить её Destination и Notes. Подробности вопросов
читать по мере необходимости, решения хранить в комментариях их разрешения.

## Wayfinding operations

- Карта — issue с меткой `wayfinder:map`. Дочерние вопросы — native sub-issues.
- Тип вопроса задаёт метка `wayfinder:grilling`, `wayfinder:research`,
  `wayfinder:prototype` или `wayfinder:task`; создавать метки по необходимости.
- Блокировки — native issue dependencies (`blocked by`), доступные в GitHub UI
  через Relationships → Mark as blocked by. Создавать вопросы до связей.
- Frontier: открытые дочерние вопросы без открытых блокирующих вопросов
  и без assignee, в порядке списка sub-issues карты.
- Claim: назначить вопрос на ведущего разработчика до начала работы.
- Resolve: опубликовать ответ комментарием, закрыть вопрос, добавить в
  Decisions so far карты одну строку с сутью и ссылкой на ответ.
- В тексте для человека ссылаться на вопросы по названию. Детали решения
  остаются в его вопросе; карта служит индексом.
- HITL-вопросы разрешаются обсуждением с пользователем. Утверждение
  спецификации требует явного ответа о конкретной опубликованной версии.

Использовать доступный авторизованный GitHub API/connector или `gh`.
Если нужной операции нет в инструменте, использовать авторизованный браузер
и штатные sub-issues/Relationships, сохраняя ту же модель трекера.
На момент создания карты коннектор читал репозиторий, но запись возвращала
`403 Resource not accessible by integration`; создание и связи проверены
через браузер. При следующей сессии проверять актуальные возможности доступа.

Исследовательские отчёты публиковать на отдельной ветке `research/<name>`
со ссылкой на файл в конкретном коммите из ответа вопроса. Проверку
документации отличать от успешного запуска инструментов в проекте.
